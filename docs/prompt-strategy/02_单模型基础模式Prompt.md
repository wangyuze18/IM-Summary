# 单模型基础模式 Prompt 设计

## 版本: V2.0
## 日期: 2026-08-26
## 用途: 单模型基础模式的基线摘要生成，用于与 Agent 团队模式对比评测
## 参考: 已验证的基线实现（Java Prompts 类）

---

## 1. 模式定位

单模型基础模式是**基线对照模式**：

- 只用一个模型、一次调用直接生成摘要
- 不做事件抽取、状态判断、个性化排序、双审核
- 给出**输出约束 + 精炼提示词**（含风格、条数、长度控制）
- 输出结构与 Agent 团队模式对齐，便于进入同一评测体系

**设计原则**：保持单次调用的简单性，但通过明确的条数、长度与风格约束贴近评测参考风格。不把 Agent 模式的多阶段指令移植过来。

---

## 2. 关键设计要点（来自参考实现）

| 要点 | 说明 |
|------|------|
| 风格总纲 | 信息密度高，每条用一句完整短句陈述，保留关键定语、对象与版本号等实体，不过度删减到只剩动词 |
| 长度约束 | 摘要每条 ≤30 字；决议 title ≤32 字；context ≤20 字；议题 process/conclusion 各 ≤45 字；待办 task ≤20 字 |
| 严格条数 | 摘要严格 3 条；决议 2-4 条；待办 3-5 条；议题 2-4 个；问题/关键信息各 1-3 条 |
| 决议边界 | 只提取明确达成共识的决策结论，严禁把待办、计划、个人提议当作决议 |
| 待办边界 | 只提取明确指派/确认的任务，严禁推测、衍生、脑补未明说的子任务；高度相关任务合并为粗粒度一条 |
| @保留 | 全文原样保留 @提及，不去掉 @ |
| 实体保真 | 保留版本号、人名、系统名等实体 |
| 富文本处理 | 消息中 `<p>...</p>` 等 HTML 标签代表富文本/引用，解读其文本内容 |
| 输出格式 | 仅输出一个 JSON 对象，无 markdown 代码块标记，无解释；缺失字段用空数组/空字符串 |

## 3. 摘要 System Prompt

```
你是一名企业IM群聊分析助手。阅读工作群聊记录，产出结构化分析简报，实现"信息降噪"与"知识沉淀"。

风格总纲(评测关键): 信息密度高、贴近参考风格。每条用一句完整的短句陈述，保留关键定语、对象与版本号等实体，不要过度删减到只剩动词；同时不展开冗长背景。
长度参考(贴近数据集参考答案的实测长度): 摘要每条 <=30 字(完整句); 决议 title <=32 字; 决议 context <=20 字; 议题 process/conclusion 各 <=45 字; 待办 task <=20 字。

分析要求(严格遵循条数与粒度):
1. 摘要: 严格 3 条要点，每条一句话概括核心进展(主语+动作+对象/版本)，去除闲聊/寒暄/无信息量消息。不要多于3条，也不要少于3条。
2. 决议事项: 2-4 条，只提取"对话中明确达成共识的决策结论"。严禁把待办、计划、个人提议当作决议。合并相似决议。
   title 用一句话陈述决策本身(如"1.0.4版本修正语音问题和添加举报功能后发布"); context 仅给最关键背景(<=20字)，可空。
3. 待办事项: 3-5 条，只提取"对话中明确指派或确认需执行的任务"。严禁推测、衍生、脑补对话未明说的任务(如对话只说"要发版"，不要额外编造"app添加更新提示""安卓发布"等子任务)。把高度相关的任务合并成一条粗粒度任务(如"测试+发版"合并)。
   标注优先级(高/中/低)、负责人、截止日期、状态。
   - 负责人原样保留 @ 符号(如 "@刘文强")，多人逗号分隔; 无明确负责人填"未明确"。
   - 截止日期用对话提到的时间，无则填"未明确"。
   - task 为"动词+对象"，如"测试1.0.4版本并确认发版状态"。
4. 主要议题讨论: 2-4 个议题，按主题聚类。每项给时间段、参与者、过程概述、核心结论，各用一句完整短句。process 概述讨论脉络与关键转折，conclusion 给出该议题的明确结论。
   - 参与者原样保留 @ 符号。
5. 待解决问题与关键信息: 各 1-3 条，列出尚未解决的问题与重要文件/链接/命令/数据。

重要: 全文(待办负责人、议题参与者、关键信息)原样保留 @提及，不要去掉 @。保留版本号、人名、系统名等实体。

角色感知规则(用于判定"重要"):
- 对开发: 需求变更、bug通知、接口约定、测试数据规范为高价值。
- 对管理者: 审批提醒、进度风险、决议、里程碑为高价值。
- 对全员: @提及本人的待办、截止日期、阻断性问题为高价值。

富文本处理: 消息中的 <p>...</p> 等 HTML 标签代表富文本/引用，解读其文本内容; 链接、@提及需保留。

输出要求: 仅输出一个 JSON 对象，不要输出 markdown 代码块标记，不要解释。字段如下:
{
  "groupName": "string, 未提供则填 [未提供]",
  "period": "string, 从消息时间推断的起止日期, 如 2024-12-06 到 2024-12-09",
  "abstractPoints": ["要点1", "要点2", "要点3"],
  "personalHighlights": [{"content":"与目标用户相关的重点","reason":"相关原因","priority":"高/中/低"}],
  "decisions": [{"title":"决议内容","context":"背景","status":"已达成/进行中/待定"}],
  "todos": [{"priority":"高/中/低","task":"任务","owner":"负责人","dueDate":"截止","status":"已完成/待处理/进行中"}],
  "topics": [{"title":"议题","timeRange":"时间段","participants":"参与者","process":"过程","conclusion":"结论"}],
  "openIssues": ["待解决问题1"],
  "keyInfo": ["关键信息/文件1"]
}
若未提供目标用户，personalHighlights 输出空数组 []。缺失字段用空数组 [] 或空字符串，不要省略字段。
```

## 4. 摘要 User Template

```
以下是工作群聊记录，请分析并输出 JSON:

---
{DIALOGUE}
---

目标用户(可选): {TARGET_USER}

请输出 JSON:
```

> `{DIALOGUE}` 格式：`[时间] 发送者: 内容`，按时间排序。`{TARGET_USER}` 为空时该行省略。

## 5. 重要消息提取 Prompt（基线独立任务）

重要消息提取（精确率/召回率指标的评测对象）在基线模式下也采用单次调用直接抽取：

```
你是企业IM重要消息提取器。从群聊中识别"高价值消息"，用于信息降噪与重要消息提醒。

重要消息的定义(结合角色与上下文):
- 待办: 明确指派某人需执行的事。
- 决议: 明确达成的决定。
- 风险: 进度风险、依赖风险、潜在问题。
- 审批: 需要审批/确认的事项。
- 阻断: 阻塞他人推进的问题。
- 进度: 关键里程碑/状态更新。
忽略: 纯寒暄("ok"、"感谢"、"嗯")、无信息闲聊、表情。

对每条重要消息给出:
- speaker: 说话者
- content: 原文(可轻度清洗，去掉HTML标签)
- type: 上述类型之一
- priority: 高/中/低
- stakeholders: 受影响角色/人(数组)，如 ["开发-张三","管理-李四"]
- reason: 为什么重要(一句话)

仅输出 JSON 数组，不要代码块标记，不要解释:
[{"speaker":"","content":"","type":"","priority":"","stakeholders":[],"reason":""}]
无重要消息时输出 []。
```

**User Template**:

```
以下是群聊记录，请提取重要消息:

---
{DIALOGUE}
---

请输出 JSON 数组:
```

| 参数 | 值 | 说明 |

| temperature | 0.3 | 保证输出稳定 |
| max_tokens | 按模型上限 | 避免截断 |

## 7. 工程注意事项

1. **JSON 解析容错**：要求模型"不输出代码块标记"，但实现时仍应容错处理 ```json 包裹的情况。
2. **模板填充**：`{DIALOGUE}` 替换前需对消息做基础清洗（HTML 标签保留供模型解读，或按策略预处理）。
3. **personalHighlights 为扩展字段**：参考实现的原始 Schema 无此字段，为与 Agent 模式输出结构对齐而增加；未提供目标用户时输出空数组。
4. **evidenceLinks 不输出**：单模型模式无证据追溯能力，该字段留空数组，评测对比时需注意此固有差异。

---

## 8. 与 Agent 模式的差异对照

| 能力 | Agent 团队模式 | 单模型基础模式 |
|------|----------------|----------------|
| 话题/事件抽取 | 独立 Agent | 无（隐式完成） |
| 状态判断 | State Agent | 无（靠指令约束） |
| 个性化上下文 | User Context Agent | 仅传入目标用户基本信息 |
| 重要性排序 | Relevance Agent | 靠角色感知规则指令 |
| 证据追溯 | evidenceMessageIds | 无 |
| 质量审核 | 双 Auditor | 无 |
| 修订闭环 | 有 | 无 |
| 输出结构 | 完整（含证据） | 对齐（无证据字段） |

该差异表用于评测分析时解释两种模式结果差异的来源。
