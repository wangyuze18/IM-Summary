## 1. 设计边界与核心约束

1. **离线会话是唯一数据入口**：桌面端上传本地文件，后台完成解析、标准化、持久化。
2. **四类底层数据**：IM 消息、用户画像、组织与协作关系、群组上下文。不引入外部项目/任务上下文。
3. **纯文本处理**：当前阶段只处理文本消息，不涉及图片/文件等多模态内容。
4. **双分析模式**：支持 **Agent 工作流团队模式** 与 **单模型**，便于对比评测。
5. **模型不绑定**：后端不内置固定模型，由前端配置接口协议 + URL + API Key，后端据此调用。
6. **无个人登录**：不设计账号体系；部署级鉴权可选。
7. **Demo 级别**：不考虑高并发、负载均衡、水平扩展；以功能正确性优先。

### 模块职责

| 模块 | 职责 |
|------|------|
| API Layer | 统一 HTTP/WebSocket 入口 |
| Session Service | 会话、群聊、成员、组织关系、版本管理 |
| Analysis Service | 分发分析请求到 Agent 编排器或单模型运行器 |
| Agent Orchestrator | 编排 8-Agent 双任务 DAG、并行、修订闭环 |

| Evaluation Service | 计算评测指标，支持双模式对比与历史导出 |

### 跨源访问（CORS，V5.3 新增）

桌面端渲染进程直接以 `fetch` 调用 `/api/**`（开发模式 Origin 为本地 dev server，打包后为 `null`），后端在 API Layer 对 `/api/**` 开启 CORS：允许任意 Origin / Method / Header，暴露 `Content-Disposition`（文件下载建议文件名）。Demo 级本地部署，不做 Origin 白名单限制。

## 3. 模型配置与管理（核心新增）

### 3.1 ModelApiProfile

模型不固定，由用户在前端配置。后端只保存配置与凭据引用。

```
ModelApiProfile
- profileId
- displayName            # 用于识别，如"主力大模型"
- providerType           # openai-compatible | anthropic | custom
- baseUrl                # API 地址
- modelName              # 实际调用的模型名
- apiKeySecretRef        # 指向 Credential Store 的引用，不存明文
- thinkingModeSupported  # 是否支持思考/推理模式（探测得到）
- connectionStatus       # untested | testing | available | failed
- lastTestedAt
- lastErrorMessage
- enabled
- createdAt / updatedAt
```

### 3.2 providerType 与协议适配

后端通过 **Adapter 模式** 适配不同接口协议，对上层屏蔽差异。

| providerType | 请求格式 | 说明 |
|--------------|----------|------|
| `openai-compatible` | `/v1/chat/completions` | 兼容 OpenAI 格式的大多数服务（OpenAI、DeepSeek、Qwen、本地 Ollama 等） |
| `anthropic` | `/v1/messages` | Anthropic Claude 原生格式 |
| `custom` | 可配置 | 预留，按需扩展 |

**Adapter 职责**：
- 构造该协议的请求体（messages、system、参数）
- 解析该协议的响应体，统一转为内部 `ModelResponse`
- 透传/映射思考模式参数（见 3.4）

### 3.3 连接测试与模型状态检测

用户配置后可触发"测试连接"，后端执行两级检测：

```
第 1 级：可用性检测
  发送最小请求（如 "ping" 或空内容补全）
  → 成功：connectionStatus = available
  → 失败：connectionStatus = failed，记录 lastErrorMessage

第 2 级：思考模式探测（仅在可用性通过后）
  携带思考模式参数发送一个简短请求
  → 响应正常且包含推理特征：thinkingModeSupported = true
  → 响应报错或不支持：thinkingModeSupported = false
```

**状态含义**：
- `connectionStatus`：模型当前是否可调用
- `thinkingModeSupported`：该模型是否能开启思考/推理模式

> 思考模式探测不强制要求成功；某些模型不支持但不影响正常使用，只是前端显示"思考模式不可用"。

### 3.4 思考模式的使用

- 若 `thinkingModeSupported = true`，Agent 调用时可选择开启思考模式（通过请求参数）。
- 思考模式适用于需要复杂推理的 Agent（如 State Agent、Summary Agent）。
- 是否开启由模型配置中的一个开关控制（默认关闭以节省成本，可手动开启）。

### 3.5 Agent 与模型的绑定

延续"默认 + 覆盖"机制：

```
AgentModelSettings
- defaultProfileId          # 默认使用的模型档案
- useThinkingMode           # 是否默认开启思考模式
- bindings[]
  - agentKey                # context_event | state | user_context | relevance | summary | factual_auditor | personalization_auditor | single_model | evaluation_judge
  - profileId?              # null = 继承默认
```

### 3.6 Run 配置快照

启动分析前，解析"默认配置 + Agent 覆盖"，生成不可变 `RunModelConfigSnapshot`。运行中修改配置不影响当前 Run。快照只记录 profileId、modelName、协议、凭据引用版本，不复制明文密钥。

### 3.7 模型列表自动获取

配置档案时，前端可请求后端自动获取该服务支持的全部模型名，供用户下拉选取，避免手填出错。

- 端点：`POST /api/model-profiles/models`，body 与 `/test` 一致：携带 `profileId` 表示已保存档案（未给 `apiKey` 时后端解密已存凭据），否则按草稿 `providerType + baseUrl + apiKey` 探测。
- 仅 `openai-compatible` 协议支持：请求 `GET {baseUrl}/models`（baseUrl 末尾自动归一化，不重复追加路径），解析响应 `data[].id`，按名称排序返回 `{ models: string[] }`。
- `anthropic` / `custom` 协议返回统一错误体 `{ errorCode, message }`（提示该协议暂不支持模型列表获取），前端保留手填输入作为回退。
- 响应任何情况下不含明文 API Key。

## 4. 双分析模式（核心新增）

### 4.1 模式定义

| 模式 | 说明 | 用途 |
|------|------|------|
| `agent-workflow` | 完整 8-Agent 双任务协同工作流 | 主分析模式，质量优先 |
| `single-model` | 单模型一次调用直接产出摘要 | 基线对照，便于对比评测 |

两种模式**共享相同的输入数据**（同一份会话），产出**相同结构的 SummaryResult**，从而可以进入同一评测体系对比。

### 4.2 Agent 工作流团队模式

完整执行 8-Agent（新增 Importance Extractor）：

```
Context & Event → [State ∥ User Context] → Personalized Relevance
→ Summary → [Factual Auditor ∥ Personalization Auditor] → pass/revise
```

详见《企业IM Agent数据与工作流设计规范》与《Prompt 设计总纲》。

### 4.3 单模型

- **目标**：用最简单的方式生成摘要，作为基线。
- **实现**：将完整消息 + 输出 Schema 约束 + 简单提示词，一次性交给单个模型。
- **不做**：事件抽取、状态判断、个性化排序、双审核。
- **输出**：与 Agent 模式相同的 `SummaryResult.structured` 结构，便于对比。
- **Prompt**：见《02_单模型模式Prompt》。

### 4.4 模式选择与运行

启动分析时，前端指定 `mode`：

```
POST /api/sessions/{id}/runs
{
  "targetUserId": "可选",
  "mode": "agent-workflow | single-model"
}
```

每次运行记录 `mode`，AgentRun 扩展字段：

```
AgentRun
- runId / sessionId
- mode                    # agent-workflow | single-model
- modelConfigSnapshotId
- status / overallProgress / elapsedMs
- agentSteps[]            # single-model 模式只有 1 个 step
- revisionNo
```

## 5. 离线会话上传与导入

流程与 V4.0 一致，此处简化说明：

```
1. 桌面端选择文件（支持多选/拖拽多个，批量导入）→ 逐个上传到 Import Service
2. 后台对每个文件独立执行结构解析 + 字段标准化（不做业务推断）
3. 逐个返回 ERROR / WARNING / INFO 与预览；单文件失败不阻断其他文件
4. 用户确认 → 逐个创建 ConversationSession，持久化四类数据（批量时逐文件创建，失败项记录原因可重试）
5. 导入成功不自动分析，用户手动触发
```

**标准导入对象**：

```
OfflineSessionImport
- schemaVersion
- session: title, targetUserId?
- group: GroupInfo
- messages: ChatMessage[]
- users: UserProfile[]
- relationships: RelationshipEdge[]
- goldenSummary?: GoldenSummaryInput
```

**校验分级**：
- `ERROR`：结构无法解析、messageId 冲突 → 阻断导入
- `WARNING`：画像缺失、关系为空 → 允许导入并记录
- `INFO`：无黄金摘要、可选字段为空 → 正常导入

**新版数据集格式兼容（V5.2 新增）**：

支持《企业IM合成对话数据集格式设计规范 V1.0》的评测数据集样本（顶层含 `scenarioPlan / group / users / relationships / messages / groundTruth / qualityAudit`），与标准导入对象双格式并存。导入时自动探测（存在 `groundTruth` 节点即判定为数据集格式）并**归一化为内部既有形态**，下游 Agent 编排、前端展示、评测链路零改动：

| 数据集字段 | 归一化结果 |
|------|------|
| `messages[].senderDisplayName` | `sender`（补 `@` 前缀，与内部格式一致） |
| `users[].displayName / positionName` | `users[].name / position` |
| `relationships[].source / target` | `sourceUserId / targetUserId` |
| `groundTruth.goldenSummary`（结构化对象） | 渲染为 Markdown 文本存入黄金摘要；为 `null` 时视为未携带（会话不可评测） |
| `group.groupName` + `scenarioPlan.evalSampleId` | 会话标题（如 `订单中心后端群（E001）`） |
| `group.targetUser` | `session.targetUserId` |

红线约束：`scenarioPlan`、`qualityAudit`、`groundTruth.eventLedger` 属元信息，仅存储溯源，**不进入模型上下文**；数据集消息禁含 URL/附件的约束由数据集生成侧保证，导入校验不对此重复阻断。

## 6. 核心领域对象

| 对象 | 职责 | 关键边界 |
|------|------|----------|
| ConversationSession | 一次离线群聊分析会话 | 来源、当前摘要、导入状态 |
| GroupInfo | 群组上下文 | 群名、成员、时间范围 |
| ChatMessage | 原始消息事实 | 只读保真，不被 Agent 改写 |
| UserProfile | 用户画像 | 非事实证据 |
| RelationshipEdge | 组织/协作关系 | 有方向，只用于相关性 |
| EventLedger | 统一事件账本 | 事实主线，关联 messageId |
| UserContextCard | 目标用户最小上下文 | 个性化主线 |
| PersonalizedEventLedger | Event + 相关性 | 不修改事实字段 |
| AgentRun | 一次完整分析运行 | 记录 mode、配置快照 |
| AgentStepRun | 单节点运行 | 状态、耗时、错误、重试 |
| SummaryResult | 最终摘要 | Markdown + structured + evidence |
| AuditReport | 审核结果 | 事实/个性化分开 |
| GoldenSummary | 可选黄金摘要 | 独立版本，不参与生成 |
| EvaluationResult | 对比评测结果 | 绑定 summaryVersion + goldenVersion |
| ModelApiProfile | 模型配置档案 | 凭据引用、状态、思考模式 |

## 7. Event Ledger 与事件生命周期

```
EventRecord
- eventId / topicId
- eventType: proposal | decision | task | risk | problem | information | status_update
- content
- participants[]
- owner[]? / dueDate?
- state: proposed | confirmed | active | in_progress | resolved | superseded | cancelled | rejected | unknown
- evidenceMessageIds[]
- relatedEventIds[]
- supersedes?
- confidence?
```

**核心规则**：
- 重要事件必须关联 `evidenceMessageIds`
- proposal 不自动进入 decisions，只有 confirmed 才可
- 只有明确指派/确认才产生 task 的 owner
- 负责人/截止未明确则保留"未明确"，不猜测
- 职位/职责/关系不写入事实字段

## 8. SummaryResult 与修订闭环

```
SummaryResult
- summaryId / sessionId / runId / version
- mode                       # agent-workflow | single-model
- markdown
- structured:
  - abstractPoints[]
  - decisions[]
  - todos[]
  - topics[]
  - openIssues[]
  - keyInfo[]
- evidenceLinks[]
- auditStatus
- generatedAt
```

**修订闭环**（仅 agent-workflow 模式）：
- 措辞/Schema 问题 → 回 Summary 修订
- 事件状态错误 → 回 State
- 关系理由错误 → 回 User Context / Relevance
- 事件抽取错误 → 回 Context/Event
- 每次修订 `revisionNo++`，超过上限进入 warning/failed，避免无限循环

## 9. 黄金摘要与评测服务（核心增强）

### 9.1 黄金摘要

- **唯一来源：随会话导入**。导入文件含 `goldenSummary` 字段时，确认导入时直接持久化并立即可用；不提供手动输入/上传接口，避免非标准来源的处理与评测口径问题
- 可选携带，独立版本（`goldenVersion` 递增，仅由重新导入触发）
- 不参与生成与审核，只用于评测与前端对照展示；无黄金摘要时评测返回 `NOT_EVALUABLE`
- 导入携带的结构化黄金摘要与智能摘要使用**同一 Markdown 渲染器**渲染（模式标注为“黄金摘要（人工参考）”），便于人工逐栏对照
- 内容在线查看（V5.4 新增）：`GET /api/sessions/{id}/golden-summary` 返回 `{ goldenProvided, goldenVersion, content }`，未携带时 `goldenProvided=false`、content 为 null

### 9.2 评测指标

```
EvaluationResult.metrics
- accuracy                      # 准确率
- recall                        # 召回率
- keyInformationOmissionRate    # 关键信息遗漏率
- rougeL                        # ROUGE-L
- llmScore                      # 综合质量评分（LLM Score，0-100，越高越好）
```

不包含 BERTScore 与主观综合评价。`llmScore` 由**评测判分模型**（绑定键 `evaluation_judge`，可在模型设置中单独指定，未绑定时继承默认档案）对生成摘要与黄金摘要整体评判产出，从忠实性、完整性、结构清晰度、语言精炼度四个维度综合打分。

### 9.3 评测历史记录（新增）

每次评测生成一条记录并持久化，支持查询、筛选与导出：

```
EvaluationRecord
- evaluationId
- sessionId
- summaryVersion
- goldenVersion
- mode                        # agent-workflow | single-model
- modelSnapshotId             # 使用的模型配置
- metrics: {accuracy, recall, keyInformationOmissionRate, rougeL, llmScore}
- evaluatedAt
```

**版本失效规则**：
- 摘要新版本或黄金摘要新版本 → 旧评测记录标记 `outdated`
- 历史记录保留，不被删除

### 9.4 双模式对比说明（人工进行）

系统**不提供自动对比能力**。两种模式的评测结果均作为独立的 EvaluationRecord 持久化保存，记录中包含 `mode` 字段。用户通过评测历史列表查看、筛选和导出不同模式的记录，由人工进行对比分析。

### 9.5 评测导出

支持导出评测历史：

```
GET /api/evaluations/export?sessionId={id}&format=json|csv|markdown
```

- `json`：完整结构化记录
- `csv`：指标表格，便于人工对比分析（可按 mode 列筛选）
- `markdown`：可读报告

## 10. 群成员与组织关系服务

```
OrganizationGraph
- nodes[]: userId, employeeNo, displayName, positionCode, positionName
- edges[]: edgeId, sourceUserId, targetUserId, relationType, direction, label, scope?
```

- 只返回当前群成员与必要关系，不加载完整企业组织图
- 颜色/布局由前端处理，后端只返回 positionCode 与 relationType；关系边统一实线展示并标注中文关系名称，由前端负责渲染（V5.5）
- 关系边字段兼容：端点优先取 `sourceUserId` / `targetUserId`，兼容数据集格式 `source` / `target`；`label` 缺省回退 `relationType`，`scope` 原样透传（V5.5）
- 关系缺失时只返回成员节点，不猜测边

## 11. Web API 设计

### 11.1 REST 接口

| 能力 | 接口 | 说明 |
|------|------|------|
| 导入预检查 | `POST /api/imports/validate` | multipart file → importId + 校验 + 预览 |
| 确认导入 | `POST /api/imports/{id}/confirm` | importId → sessionId |
| 会话列表 | `GET /api/sessions` | query/page/status |
| 会话详情 | `GET /api/sessions/{id}` | group/messages/members/result |
| 启动分析 | `POST /api/sessions/{id}/runs` | targetUserId? + **mode** → runId |
| 运行状态 | `GET /api/runs/{runId}` | overallProgress + elapsedMs + steps |
| 摘要结果 | `GET /api/sessions/{id}/summary` | 当前 SummaryResult |
| 组织关系 | `GET /api/sessions/{id}/organization` | OrganizationGraph |
| 黄金摘要内容 | `GET /api/sessions/{id}/golden-summary` | goldenProvided + goldenVersion + content（Markdown）；未携带时 goldenProvided=false |
| 启动评测 | `POST /api/sessions/{id}/evaluations` | summaryVersion + goldenVersion + mode |
| 评测历史 | `GET /api/sessions/{id}/evaluations` | EvaluationRecord[]，支持按 mode 筛选；无黄金摘要时启动评测返回 `409 NOT_EVALUABLE` |
| 评测导出 | `GET /api/sessions/{id}/evaluations/export?format=csv\|json\|markdown` | 下载流，供人工对比分析 |
| 模型配置列表 | `GET /api/model-profiles` | masked profiles + 状态 |
| API Key 明文获取 | `GET /api/model-profiles/{id}/api-key` | 解密返回 `{ apiKey }`（V5.4 新增，Demo 级本地产品专用）；其余所有响应仍仅掩码 |
| 新增/更新模型 | `POST/PUT /api/model-profiles` | profile + optional apiKey |
| 测试模型连接 | `POST /api/model-profiles/test` | 支持已保存档案与未保存草稿；返回 connectionStatus + thinkingMode |

## 12. 版本、一致性与不可变快照

1. ConversationSession 保存导入版本；ChatMessage 原文不被 Agent 修改
2. 每次 AgentRun 固化 messagesVersion、画像/关系版本、RunModelConfigSnapshot
3. EventLedger、AuditReport、SummaryResult 全部绑定 runId
4. 重新分析创建新 runId 和 SummaryResult.version，旧结果保留
5. GoldenSummary 独立递增；EvaluationResult 绑定 summaryVersion + goldenVersion
6. 模型配置更新只影响后续 Run，不回写历史
7. 服务器端版本号是唯一可信来源，桌面端缓存不参与版本判定

## 13. 错误、重试与降级

| 场景 | 后台策略 | 桌面端表现 |
|------|----------|------------|
| 文件上传失败 | 保持临时状态，可重传 | 导入向导提示重试 |
| 解析错误 | 返回字段/行号/原因 | 阻断导入 |
| 用户画像缺失 | 继续；User Context 降级 | 提示个性化下降 |
| 关系缺失 | 不推断关系 | 组织图只显示节点 |
| 模型配置失效 | Run 启动前阻断 | 提示进入模型设置 |
| 模型连接失败 | 返回 connectionStatus=failed | 显示错误摘要 |
| 单 Agent 调用失败 | 有限重试；保留已完成 Step | 进度区显示失败节点 |
| 桌面端断线 | Run 继续；状态写 DB | 重连后恢复 |
| Auditor 不通过 | 定向修订；超次数 warning/failed | 显示修订中/需关注 |
| 评测失败 | 不影响 SummaryResult | 摘要仍可查看/导出 |

## 14. 安全与隐私边界

- 不设计个人账号；Web 后台部署于受控/内网环境，公网可加部署级鉴权
- API Key 只进入 Credential Store；任何接口、日志、异常、导出不返回明文
- Agent 最小权限：State 不读画像/关系；Factual Auditor 不需完整关系图
- 限制调试日志重复记录原始消息正文
- 模型调用只发送当前 Agent 必需数据
- 删除会话时删除其消息、事件、摘要、评测、导入引用；全局模型配置不随之删除

## 15. 端到端运行流程

```
1. 桌面端选择离线会话文件上传，后台返回预检查结果
2. 用户确认 → 后台标准化并持久化四类数据，创建 ConversationSession
3. 用户在模型设置中配置模型（协议+URL+Key），测试连接与思考模式
4. 用户选择目标用户 + 分析模式（agent / single），点击开始分析
5. 后台校验模型配置，创建 RunModelConfigSnapshot 和 AgentRun
6a. agent 模式：Context & Event → State ∥ User Context → Relevance → Summary → 双 Auditor
6b. single 模式：单模型一次调用生成结构化摘要
7. 固化 SummaryResult，通过实时通道通知 run.completed
8. 若导入文件携带 GoldenSummary → 已随导入持久化（产生 goldenVersion）；未携带则不提供评测入口
9. 启动评测 → 计算四项指标，写入 EvaluationRecord
10. 用户可查看评测历史（按模式筛选）、导出评测结果；对比分析由人工完成
```

## 16. 后端验收清单

1. 架构为 Desktop App → Web API/WebSocket → Web Backend，不依赖桌面本地业务服务
2. 离线文件经后台上传、预检查、确认导入并持久化
3. 四类底层数据边界正确，无外部项目/任务上下文
4. 支持 **agent-workflow** 与 **single-model** 双分析模式，产出相同结构摘要
5. 模型配置支持 openai-compatible / anthropic / custom 协议，Adapter 适配
6. 模型状态检测：可用性（connectionStatus）+ 思考模式（thinkingModeSupported）
7. Event Ledger 事实可回溯 messageId；职位/关系不改变事实
8. 模型配置支持多 profile、默认绑定、单 Agent 覆盖、测试连接、Run 快照
9. 桌面端通过实时通道获取 overallProgress、elapsedMs、AgentStep 状态
10. 桌面端断线/退出不影响已启动 Run，重连可恢复
11. 黄金摘要仅来自导入携带；摘要评测含准确率、遗漏率、文本相似度、LLM 评分；重要消息有黄金标注时评测精确率与召回率
12. 评测历史记录持久化（含 mode 字段），支持按模式筛选与 json/csv/markdown 导出；不提供自动对比能力
13. 摘要、黄金摘要、评测均版本化，旧结果不被静默覆盖
14. 组织关系接口只返回当前群必要节点/边，缺失不猜测
15. API Key 不明文保存/返回；普通配置只存 secretRef
16. Demo 级别，不实现高并发/分布式能力

## 17. V5.5 双任务架构重大调整

- 每次 Run 同时完成两个任务：结构化摘要生成、从原始消息逐条抽取重要消息；二者合并进同一 `SummaryResult.structuredJson`，重要消息字段为 `importantMessages`。
- 团队工作流新增 `importance_extractor` 阶段，输入原始消息、已校验事件状态、相关性排序和用户画像；抽取结果随摘要一同进入事实与个性化审核，形成质量闭环。
- 单模型模式使用 `single_model` 与 `importance_extractor` 两个直接任务，不使用事件校验与审核闭环，作为基线对照。
- `importantMessages` 条目字段固定为 `speaker/content/type/priority/stakeholders/reason`；`content` 保留原文，仅轻度清除 HTML。
- 黄金标注新增可选 `importantMessagesJson`。数据集可在 `groundTruth.importantMessages`（推荐）或 `groundTruth.goldenSummary.importantMessages` 提供；现有样例未补标时重要消息指标保持 `null`，禁止伪造满分。
- 统一评测指标为：摘要准确率、关键信息遗漏率、文本相似度、LLM 文本评分、重要消息精确率、重要消息召回率。
