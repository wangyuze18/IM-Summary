# 后端设计文档：双任务证据协作架构

## 1. 目标与边界

系统处理离线企业 IM 群聊，同时输出结构化摘要和重要消息。摘要负责压缩一段时间内的工作进展；重要消息负责保留值得提醒的单条原始消息，并按受影响角色/人员组织。二者共享输入但评测目标不同，因此生成、审核和评测必须避免相互污染。

系统不提供账户个人视角，也不维护目标用户或个人关注项。组织关系模型中的边端点仍使用 `sourceUserId` / `targetUserId`，它们只是图结构字段。

## 2. 设计假设

工作群聊包含交叉话题、口语省略、回复链、重复转述以及状态覆盖。若模型直接生成，主要错误来自：

1. 将提议或待办误判为决议；
2. 使用已被更新或取消的旧状态；
3. 补造负责人、截止日期或实体；
4. 重要消息抽取混入寒暄，或遗漏阻断和关键进度；
5. 把多条消息改写合并后冒充“原始消息”。

团队模式通过显式事件层、状态层和任务专属审校来处理这些错误。基础模式保留最小可复现对照。

## 3. 总体架构

```text
Controller → Service → AgentOrchestrator → ModelGateway
     │           │              │              │
     │           │              ├─ PromptTemplates
     │           │              ├─ progress events
     │           │              └─ targeted revision
     │           ├─ MarkdownRenderer
     │           └─ EvaluationService
     └─ JPA/H2 repositories
```

核心模块：

- `ImportService`：校验输入、建立会话/消息/成员/关系与黄金标注。
- `AnalysisService`：建立运行记录、解析模型快照并异步调用编排器。
- `AgentOrchestrator`：执行基础模式或团队模式，保存步骤、证据和审校产物。
- `ModelGateway`：统一处理 OpenAI 兼容、自定义兼容与 Anthropic 模型调用，并按协议自动读取模型列表、检测思考模式能力。
- `MarkdownRenderer`：将结构化 JSON 渲染为无装饰表情的工作简报。
- `EvaluationService`：分离摘要四指标与重要消息两指标。

## 4. 基础模式

基础模式由两个平行模型构成：

```text
raw dialogue ─┬─ single_model          → summary JSON
              └─ importance_extractor  → importantMessages JSON
```

两个 Future 同时提交，均直接读取群名与原始消息。它们不共享事件、不读取彼此输出、不调用审核器。编排器在两个结果完成后规范化重要消息数组并合并为统一结构化结果。

这个设计是论文实验中的 baseline：与团队模式保持输入一致、重要消息模型配置一致，但去掉团队协作机制。

## 5. 团队模式

### 5.1 阶段一：事件识别

`context_event` 对群聊进行主题重建，输出原子事件和 `evidenceMessageIds`。事件描述可以规范化语言，但证据只能来自聊天消息。画像和职位用于展示角色，不可作为事实来源。

### 5.2 阶段二：状态判断

`state` 对事件赋予 `proposed`、`confirmed`、`active`、`in_progress`、`resolved`、`superseded`、`cancelled`、`rejected` 或 `unknown`。同一事项发生变更时使用 `supersedes` 建立覆盖关系。上下文事件与状态结果合并为共享证据账本。

### 5.3 阶段三：双任务并行生成

- `summary` 只从当前有效事件生成摘要结构。
- `importance_extractor` 读取原始消息与证据账本，选择可追溯的高价值消息。

并行设计避免串行等待，也避免摘要文案影响重要消息的原文抽取。共享账本提供一致的事件状态，但两个任务仍有独立输出规范。

### 5.4 阶段四：独立审核

- `factual_auditor` 检查事实忠实、覆盖、决议有效性、待办有效性、状态一致和实体保真。
- `importance_auditor` 检查精确率风险、遗漏、消息 ID/原文保真、状态与 stakeholders 依据。

两名审核器并行执行。`passed=false`、严重问题或调用异常均视为对应分支需要修订。

### 5.5 阶段五：定向修订

只把审核问题返回到失败分支：摘要问题不重跑重要消息，重要消息问题不重跑摘要。修订后只复审该分支，最多 `imsummary.max-revision` 次。达到上限仍未通过时保留结果并将运行标为 warning，避免无限循环。

## 6. 关键数据模型

### 6.1 `ConversationSessionEntity`

保存会话元数据与导入状态；不含个人目标字段。

### 6.2 `AgentRunEntity`

记录 `runId`、`sessionId`、`mode`、状态、进度、模型配置快照、开始/结束时间与警告。

模式值：

- `single-model`：基础模式；
- `agent-workflow`：团队模式。

### 6.3 `AgentStepRunEntity`

`agentKey` 可为：

- 团队模式：`context_event`、`state`、`summary`、`importance_extractor`、`factual_auditor`、`importance_auditor`；
- 基础模式：`single_model`、`importance_extractor`；
- 评测：`evaluation_judge`。

步骤状态包含 waiting、running、completed、warning、failed 与 revising 的前端映射。

### 6.4 `SummaryResultEntity`

保存最终 `structuredJson`、`markdownContent`、模式、版本、模型和耗时。团队模式额外保存：

- `eventLedgerJson`：合并后的事件状态与证据；
- `summaryAuditJson`：最新摘要审核报告；
- `importanceAuditJson`：最新重要消息审核报告；
- `evidenceLinksJson`：结果字段与消息证据关联。

历史列表接口不返回大体积审校产物，详情接口按需返回。

## 7. 重要消息数据契约

```json
{
  "importantMessages": [
    {
      "messageId": "m17",
      "speaker": "@王炳鉴",
      "content": "1.0.4 今天测试通过后发布",
      "type": "待办",
      "priority": "高",
      "stakeholders": ["开发-@刘文强", "管理-@楊キンキ"],
      "reason": "包含明确任务与截止时间"
    }
  ]
}
```

`content` 必须对应一条原消息，只允许去除 HTML 和首尾空白；不能把多条消息合并改写。编排器兼容模型返回直接数组或常见包装字段，但对外统一为 `importantMessages`。

## 8. Markdown 渲染

简报顺序为：元信息、摘要、重要消息、决议、待办、议题、待解决问题与关键信息。重要消息按 stakeholder 分组；无法确定时归入“未明确”。渲染后执行 Unicode 表情清理，但不破坏 `@`、版本号、链接和代码文本。

## 9. 评测隔离

`EvaluationService` 创建摘要副本并移除 `importantMessages` 后渲染摘要主体。摘要判官输出 accuracy、key information omission rate 和 `llm_score`；ROUGE-L 在本地计算。

重要消息判官只接收生成/黄金重要消息，输出 precision 与 recall。黄金重要消息缺失时，两项保持 `null`。因此 `llm_score` 永远不用于评价重要消息。

## 10. API 与进度

启动运行：

```http
POST /api/sessions/{sessionId}/runs
Content-Type: application/json

{"mode":"agent-workflow"}
```

不接收个人目标。运行进度通过运行查询接口和 WebSocket 事件提供；前端根据真实步骤状态驱动机器人与连接线动画，不使用定时 mock。

## 11. 失败策略

- 模型配置缺失：运行前失败并给出明确绑定键。
- 单个生成分支失败：运行失败，不伪造结果。
- 审核器失败：对应分支进入修订/警告路径，保留可诊断信息。
- 模型 JSON 不规范：提取 JSON 对象/数组并规范化；无法解析时失败。
- 无黄金摘要：不允许启动评测。
- 无黄金重要消息：摘要仍可评，重要消息两项为空。

## 12. 验证标准

- `mvn test` 通过；
- 基础模式的两个生成调用真实并行；
- 团队模式的两个生成器和两个审核器分别并行；
- 审核失败只重跑对应分支；
- Markdown 不出现装饰性表情和个人关注内容；
- 六项指标归属正确且历史可查询。
