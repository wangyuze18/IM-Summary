# 评测方案与质量验收标准

## 版本: V1.2
## 日期: 2026-08-27

---

## 1. 评测目标

| 指标 | 目标值 | 评测方式 |
|------|--------|----------|
| 摘要准确率 | ≥ 85% | 人工评估（100组真实对话） |
| 关键信息遗漏率 | ≤ 10% | 人工评估 |
| 重要消息提取精确率 | ≥ 80% | 按角色分桶评估 |
| 重要消息提取召回率 | ≥ 75% | 按角色分桶评估 |

> 注：实时性与多模态指标在当前阶段（纯文本、Demo 级）不纳入验收范围。

---

## 2. 摘要质量评测

### 2.1 准确率定义

**摘要准确率** = 摘要中正确的事实性陈述数 / 摘要中总的事实性陈述数

事实性陈述包括：
- decisions 中的每个决议条目
- todos 中的每个待办条目（含 owner、dueDate、status）
- abstractPoints 中的每个要点
- openIssues 中的每个问题
- keyInfo 中的每个信息条目

**"正确"的判定标准**:
- 该陈述在原始消息中有明确证据支撑
- 事件状态判定正确（如不误将 proposed 标为 confirmed）
- 实体名称（人名、版本号等）与原文一致
- 不存在"幻觉"内容

### 2.2 关键信息遗漏率定义

**关键信息遗漏率** = 被遗漏的关键信息数 / 原始对话中的总关键信息数

**"关键信息"的判定标准**（由标注人员确定）:
- 明确的决策/决议
- 明确指派的待办（含负责人）
- 影响后续工作的状态变更
- 重要的风险/问题报告
- 关键数据/链接/命令

### 2.3 人工评估流程

```
1. 准备：获取100组真实对话数据（由数据提供方提供）
2. 标注：人工标注每组对话的"标准答案"（参考黄金摘要格式）
3. 生成：使用系统对100组对话分别生成摘要
4. 对比：标注人员逐条对比系统输出与标准答案
5. 计分：按公式计算准确率和遗漏率
6. 分桶：按对话类型/复杂度分组统计
```

### 2.4 综合质量评分（LLM Score）

由**评测判分模型**（可在模型设置中单独绑定，未绑定时继承默认模型配置）对生成摘要与黄金摘要进行整体评判，输出 0-100 整数分，越高越好。

评分维度：
- **忠实性**：是否存在与原文不符或幻觉内容
- **完整性**：关键决议/待办/问题/信息是否遗漏
- **结构清晰度**：章节组织是否合理、层次分明
- **语言精炼度**：表述是否简洁、无冗余

分数分档：90+ 优秀；70-89 良好；50-69 一般（有明显遗漏或少量偏差）；50 以下较差。

## 3. 重要消息提取评测


### 3.1 任务定义

"重要消息提取"定义为：从原始消息列表中识别出需要被关注的消息/事件集合。

对应系统输出：Event Ledger 中 `importance = high` 的事件（个性化重点在摘要正文中体现，不单独成栏）。

### 3.2 精确率与召回率

- **精确率 (Precision)** = 系统标记为重要的事件中确实重要的数量 / 系统标记为重要的事件总数
- **召回率 (Recall)** = 系统标记为重要的事件中确实重要的数量 / 标注中所有重要事件的总数

### 3.3 按角色分桶评估

评估需按目标用户角色分组进行：

| 角色类型 | 关注重点 | 示例 |
|----------|----------|------|
| 开发工程师 | Bug、接口变更、技术方案、代码审查 | "登录接口字段变了" |
| 测试工程师 | 测试计划、缺陷、提测时间 | "明天提测，帮忙看下用例" |
| 项目经理 | 进度、风险、资源、决策 | "项目延期一周" |
| 管理者 | 审批、关键决策、跨部门协调 | "方案需要你审批" |

每个角色至少评估 20 组对话，确保样本量充足。

## 4. 评测数据格式要求

### 4.1 输入数据

遵循《企业IM Agent数据与工作流设计规范》中的标准导入格式：

```
- GroupInfo: 群组信息
- ChatMessage[]: 消息列表（含 messageId, sender, timestamp, content, mentions）
- UserProfile[]: 用户画像
- RelationshipEdge[]: 关系边
```

### 4.2 标注数据（黄金摘要）

每组对话需标注以下内容：

```
1. 关键事件列表（相当于标注的 Event Ledger）
   - 事件内容、类型、参与者、状态
2. 应提取的决议列表
3. 应提取的待办列表（含负责人）
4. 关键信息列表
5. 对各角色用户的重要事件标注
```

## 5. 回归测试策略

当修改以下内容时，需重新执行完整评测：

| 变更类型 | 回归范围 |
|----------|----------|
| 模型更换 | 全量 100 组 |
| Prompt 修改 | 全量 100 组 |
| 工作流变更 | 全量 100 组 |
| 单 Agent 参数调整 | 至少 20 组抽样 |
| Bug 修复 | 相关对话子集 + 10 组抽样 |

## 7. 双模式评测与对比流程（人工对比）

### 7.1 两种分析模式

| 模式 | 说明 |
|------|------|
| Agent 团队模式 | 完整 8-Agent 双任务工作流，质量优先 |
| 单模型 | 单一模型一次调用，基线对照 |

两种模式对**同一会话**分别运行，产出相同结构的摘要，进入同一评测体系。

### 7.2 评测历史记录要求

每次评测生成一条持久化记录，至少包含：

- 会话与版本信息（sessionId、summaryVersion、goldenVersion）
- **模式标识（agent-workflow / single-model）**
- 使用的模型配置（模型名、是否开启思考模式）
- 六项指标（摘要准确率、关键信息遗漏率、文本相似度、LLM 文本评分、重要消息精确率、重要消息召回率）
- 评测时间与有效状态（摘要/黄金摘要更新后旧记录标记过期）

### 7.3 对比流程（人工执行）

系统**不提供自动对比功能**。对比分析按以下人工流程进行：

```
1. 对同一会话分别用两种模式运行分析，各自生成摘要（评测前提：导入文件携带黄金摘要）
2. 分别对两种模式的摘要启动评测
3. 在评测历史中按模式筛选，确认两组评测记录均有效（未过期）
4. 导出评测历史（推荐 CSV 格式）
5. 在表格工具中人工对比两组指标，形成分析结论
```

### 7.4 导出格式要求

| 格式 | 内容 |
|------|------|
| CSV | 指标表格，含 mode 列，便于筛选与人工对比（推荐） |
| JSON | 完整结构化记录 |
| Markdown | 可读报告 |

## 8. 内部 Auditor 与外部评测的关系
| 维度 | 内部 Auditor | 外部评测 |
|------|-------------|----------|
| 执行时机 | 每次生成时自动执行 | 版本验收时人工执行 |
| 目的 | 实时质量把控、减少明显错误 | 验证系统整体质量达标 |
| 标准 | 结构化规则检查 | 人工对比黄金标准 |
| 产出 | AuditReport (pass/fail) | 准确率/召回率/遗漏率数值 |

内部 Auditor 是质量保障的第一道防线，外部评测是验收标准。两者互补，不可替代。

## 9. 双任务统一评测口径

| 任务 | 指标 | 可评测条件 |
|------|------|------------|
| 摘要 | 准确率、关键信息遗漏率、文本相似度、LLM 文本评分 | 存在黄金摘要 |
| 重要消息 | 精确率、召回率 | 存在人工黄金重要消息数组 |

六项指标在页面同一行展示并进入同一条历史记录。当前 `D:\qq\downloads\dataset\dataset\samples` 的 100 个样例均有 `groundTruth.goldenSummary`，但尚无重要消息黄金数组，因此摘要四项正常评测，重要消息两项必须显示“暂无标注”。推荐补标格式：

```json
"importantMessages": [
  {"messageId":"m12","speaker":"@张三","content":"原始消息","type":"待办","priority":"高","stakeholders":["开发-@李四"]}
]
```

团队工作流的预期优势来自事件状态校验、角色上下文、事实审核和定向修订，不通过修改评测口径或人为加分实现。验收时应对同一会话、同一底座模型分别运行两种模式，并报告六项指标的绝对值与提升幅度。

### 9.1 判分隔离

摘要和重要消息必须执行两次相互隔离的判分调用：

1. 摘要判分输入在服务端删除 `importantMessages`、别名字段及历史 `personalHighlights`，只输出摘要准确率、遗漏率和 `llm_score`；文本相似度在摘要主体上本地计算。
2. 重要消息判分只接收生成与黄金重要消息数组，只输出精确率、召回率，不输出或影响 `llm_score`。
3. 黄金重要消息未标注时精确率、召回率为不可评测（null/“暂无标注”），不得按空数组计满分。

### 9.2 模式对照

- 基础模式（baseline）：摘要模型和重要消息模型并行读取原始输入，互不共享中间推理，不运行审核。
- 团队模式：事件与状态 Agent 先建立共享事实链；摘要和重要消息并行生成；摘要审核器和重要消息审核器并行检查；错误反馈到生成器定向修订。
- 对照实验必须使用相同原始对话、相同黄金标注和同等级底座模型。团队模式的提升只能来自工作流，不得修改判分阈值或提示评测器偏向某模式。
